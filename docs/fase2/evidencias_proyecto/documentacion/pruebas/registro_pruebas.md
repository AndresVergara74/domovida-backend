## Ajustes detectados durante las pruebas

1. La hora de los mensajes ntfy y el conteo de "eventos hoy" usaban hora UTC del servidor (Render) en vez de la hora de Chile (diferencia de 3 horas). Corregido en ntfy (commit 1c8c203, zona America/Santiago); pendiente revisar el conteo "eventos hoy" del panel.
2. La apertura de la puerta principal genera alerta en todos los casos; debería considerar horario o contexto. **Corregido** (05-10-2026): la regla vive ahora en el backend (`reglas_puerta.py`) y alerta solo si la puerta se abre de noche (22:00 a 07:00) o queda abierta 10 minutos o más (prueba PU-04). El estado de la puerta se guarda en memoria y se reinicia si el servidor se reinicia.
3. Una alerta atendida mantiene el color rojo y no muestra la hora de atención. **Corregido** (commit bc31fb5, 05-10-2026): la alerta atendida se muestra atenuada, tachada y con la hora de atención.
4. El panel muestra Raspberry Pi y MQTT como "ONLINE", aunque en el prototipo son componentes simulados. **Corregido** (commit bc31fb5, 05-10-2026): se muestran como «SIMULADO» y ya no cuentan en el estado general del sistema.
5. El plan gratuito de Supabase pausa el proyecto tras días de inactividad; el backend en Render falla al arrancar hasta reactivarlo (incidente del 01-10-2026).
6. Los despliegues de Vercel fallaban desde el 27-09-2026 por errores de TypeScript (faltaban los tipos de Leaflet y el estado `conectado`); corregido en el commit 9b07078.
7. PR-01: el backend enviaba la notificación ntfy de forma síncrona antes del WebSocket, lo que retrasaba la alerta en el panel. Ajuste aplicado (commit 1c8c203): WebSocket primero y ntfy en segundo plano; latencia promedio bajó de 1.903 ms a 1.577 ms (−17 %). La latencia restante se explica por la distancia entre servicios (navegador en Chile → backend en Oregón → base de datos en São Paulo), propia de los planes gratuitos; la meta < 1 s requiere acercar las regiones (backend y base de datos en la misma región) en una fase de producción.
8. ntfy en Android: con la optimización de batería activa, las notificaciones llegan con retraso aunque el servidor las acepte. Mitigación: permitir uso en segundo plano y entrega instantánea en la app ntfy; documentarlo en el manual del cuidador.
9. PS-01 (autenticación de endpoints) no se ejecutó: al revisar el código se constató que la API REST no implementa autenticación (no hay token ni clave), por lo que cualquier cliente autorizado por CORS puede enviar datos o marcar alertas como atendidas. Hallazgo de seguridad: se planifica agregar una clave de API para los sensores y autenticación para el panel (Supabase Auth) antes del cierre del prototipo. La protección actual de los datos almacenados descansa en RLS (PI-03 aprobada) y en CORS. **Corregido en parte** (05-10-2026, commits 1688327 y b23df2f): `POST /api/sensor-data` exige la cabecera `X-API-Key` (módulo `backend/seguridad.py`, comparación en tiempo constante, clave en la variable de entorno `DOMOVIDA_API_KEY`); prueba PS-01 aprobada 3/3 en producción. Pendiente: autenticación del panel (inicio de sesión del cuidador) para proteger `PATCH /api/alertas/{id}/resolver`.
10. PR-01b confirma la causa de la latencia de PR-01: con backend y base de datos en la misma máquina (AWS EC2), la alerta llega en 216 ms en promedio y cumple la meta < 1 s en el 100 % de los casos. Para producción se recomienda desplegar backend y base de datos en la misma región.
11. En AWS EC2 el panel se sirve por http (sin certificado). En ese contexto el navegador desactiva la API de cifrado `crypto.subtle` y el consentimiento no puede calcular el hash SHA-256 (error "Cannot read properties of undefined (reading 'digest')"). Para producción, EC2 requiere https (dominio y certificado TLS); en Vercel (https) el consentimiento funciona. Evidencia: hallazgo_aws_http_crypto_subtle.png.
12. HL7 FHIR R4 estaba planificado para el Sprint 4 y no tenía implementación (solo la columna payload_fhir vacía). Ajuste: se implementó el 02-10-2026 un módulo de interoperabilidad (`backend/routers/fhir_router.py`) que expone los eventos como recursos Observation, validado en PI-04. Pendiente: los timestamps del simulador se envían sin zona horaria y se interpretan como UTC.
13. PR-03: el backend usa una sola base de datos a la vez (SQLite en modo borde o Supabase en la nube, según `DATABASE_URL`). Sin internet, el modo borde sigue funcionando, pero no existe una cola de eventos pendientes que se sincronice con Supabase al volver la conexión (el campo `sync_status` solo lo actualiza un trigger en Supabase). Plan: implementar almacenamiento y reenvío (store-and-forward) que guarde en SQLite con estado `pendiente` y suba los eventos cuando haya conexión.
14. PR-03: `navigator.onLine` no sirve para comprobar el corte de internet en Windows, porque los adaptadores de red virtuales lo dejan en `true` aunque no haya conexión. El script se corrigió para comprobar el acceso real intentando llegar a ntfy.sh.
15. En modo borde (SQLite) el panel sigue mostrando la tarjeta «PostgreSQL (Supabase) ONLINE», porque la etiqueta del estado del sistema es fija. Debe indicar la base de datos realmente en uso. Además, en SQLite no existe la tabla `alertas` (la crea un trigger de Supabase): las alertas se identifican por el campo `alerta` de la tabla `eventos`. **Corregido** (commit bc31fb5, 05-10-2026): el estado del sistema muestra la base de datos realmente en uso («PostgreSQL (Supabase)» o «SQLite (local, modo borde)»).
